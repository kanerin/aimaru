# PR をレビューして直し、再提出する

## これが何のためにあるか

AIMARU の自律開発は「要件 → 実装 → PR」までを回している。このスキルはその次で、
**出た PR を読んで、直せるものを直して押し戻す**。

ただし前提を正直に置く。**書いたのも直すのもマージするのも同じ AI なら、独立した
レビューにはならない。** 人間のレビューが持っている「この実装が本当に要件を満たして
いるか、外から疑う」機能は、自動化では完全には再現できない。だからこのスキルは
次の2つで擬似的に独立性を作る。

1. **PR の説明文を信じない。** 何を満たすべきかは Notion の `受入基準` から読み直す。
   実装者の自己申告ではなく、契約に照らす
2. **自分の実装を庇わない。** 同じ AI が書いた PR でも、受入基準に照らして足りなければ
   「足りない」と書く。ここで甘くすると、このスキルの存在意義が消える

## 承認の基準

**重大な問題が無ければ Approve してマージする。** 細かい好みで止めない。

止めるのは次の4つだけ。これ以外は、気になっても指摘コメントを残したうえで
マージする。

| ブロックする | 具体例 |
|---|---|
| **ランタイムエラー** | 特定の入力・状態でクラッシュする。null 参照、範囲外、未処理の例外。データが壊れる・消える |
| **セキュリティ** | 認証・権限のすり抜け、他人のデータが読める・書ける、秘密情報がバイナリやログに漏れる |
| **受入基準を満たしていない** | Notion の `受入基準` の項目が実装されていない、または明確に違う挙動になっている |
| **CI が赤い** | `analyze` の失敗、テストの失敗。機械が落ちると言っているものを人間の判断で通さない |

**ブロックしないもの**（コメントは残してよいが、マージは止めない）:

- 命名・コメント・書き方の好み
- 「別の実装方式のほうが良さそう」という設計の提案
- 将来の拡張性、今は問題になっていない性能
- スコープ外の改善案

この線引きを守ること自体が重要。**基準を都度ゆるめたり厳しくしたりすると、
何が通って何が止まるかが予測できなくなり、レビューが儀式になる。**

## 着手する前のゲート

**対象が無ければ何もせずに終わる。** レビュー待ちが無いのに PR を探し回ると、
関係ない変更に手を出し始める。

1. `develop` を base とする open な PR があるか。無ければ「レビュー対象なし」で終わる
2. その PR に**直近30分以内の push があるか**。あれば他のセッションが作業中の可能性が
   高いので触らない
3. その PR が**すでに3ラウンド以上レビューされているか**。あれば収束していないので、
   直さずに人間へエスカレーションする（後述）

複数ある場合は**古いものから1件だけ**。溜まっている PR を並行して触ると、
どれがどのレビューで直ったのか分からなくなる。

## 手順

### 1. 状況を掴む

```bash
git fetch --all --prune
```

PR の差分、CI の状態、既存のレビューコメントを読む。**過去のレビューで
「直さない」と判断されたものを蒸し返さない**ため、コメント履歴は必ず先に読む。

### 2. CI が赤ければ、まずそれを直す

赤い CI はレビュー以前の問題で、しかも原因が機械的に分かる。ログを読んで直す。

- `flutter analyze` の指摘 → 直す
- テストの失敗 → **なぜ落ちたかを切り分けてから**直す。実装が壊れているのか、
  テストが現実に追いついていないのかで対処が真逆になる
- **意図的に失敗させているテスト**（Notion の `期待結果` に「現状は失敗する見込み」と
  書かれているもの）は仕様。通すために実装を歪めない

### 3. 受入基準と突き合わせる

PR に紐づく要件を Notion で開き、`受入基準` を読む。**PR 本文の主張ではなく、
受入基準を1項目ずつ差分で確認する。**

満たしていない項目があれば、それが最優先の指摘。実装が足りないのか、
そもそも解釈が違うのかを見極める。解釈が違うなら直さずに人間へ投げる。

### 4. コードをレビューする

`/code-review` スキルを使う。このリポジトリ固有の観点は
`.claude/skills/notion-implement/references/codebase-notes.md` にまとまっているので、
先に読む。特に踏みやすいのは次。

- Firestore ルールの制約（`create` 時の `resource` は null、クエリとルールの整合）
- リマインダーの状態管理（`reminded` が予定単位でメンバー単位でない）
- table_calendar のカスタム builder が `CalendarStyle` を無視する
- 日付計算（JS の `Date` が存在しない日を繰り上げる、月境界）

### 5. 直すものと投げるものを分ける

ここが判断の中心。**全部直そうとしない。**

| 直す | 直さずコメントだけ残す |
|---|---|
| バグ、境界値の取りこぼし | 要件の解釈が割れるもの |
| テストの不足（受入基準に対応するもの） | 設計の方向性（別の実装方式の提案） |
| `analyze` の指摘、命名やコメントの明らかなずれ | スコープを広げる変更 |
| 既存の書き方から浮いている箇所 | プロダクト判断（何を作るか） |

右の列は**マージを止める理由にはならない**。コメントを残してマージし、
必要なら `docs/open-issues.md` か Notion に起票して次の周回へ送る。

要件の解釈が割れるものだけは例外で、**受入基準を満たしているか判断できない**なら
マージせずエスカレーションする。何を作るべきか分からないまま通すと、
間違ったものが積み上がる。

### 6. 再提出する

直したら同じブランチへ push する。PR は自動で更新される。

- **force push しない。** 履歴が消えると、前回のレビューで何が直ったか追えなくなる
- **元の実装者の意図を勝手に変えない。** 直すのは欠陥であって、書き方の好みではない
- スコープを広げない。レビュー中に気づいた別件は PR コメントか `docs/open-issues.md` へ

push したら PR にレビュー結果をコメントする。次のラウンドの自分が読む前提で書く。

```markdown
## レビュー（Nラウンド目）

### 直したもの
- <指摘> → <どう直したか>

### 直さなかったもの
- <指摘> → <なぜ人間の判断が要るか>

### 受入基準の充足
- <各項目> → 満たす / 満たさない（理由）

### テスト
- 実行結果: <通った件数 / 実行できなかったものと理由>
```

### 7. Approve してマージする

**マージ前に必ずこの順で確認する。ひとつでも欠けたらマージしない。**

1. **CI が緑になっている** — 自分の修正を push した後の実行結果を見る。
   前回の緑を根拠にしない。押し戻した変更で落ちることがある
2. **ブロック対象の4つが無い** — ランタイムエラー / セキュリティ / 受入基準の不足 / CI 赤
3. **他のセッションが同じ PR を触っていない** — 直近30分以内の他者 push が無い

満たしていれば Approve して `develop` へマージする。マージ後、作業ブランチは
削除してよい。

### 8. `release-stg` まで進める

`develop` へマージしたら、そこで止めずに `release-stg` へも流す。

```
作業ブランチ → develop → release-stg → release-prd
                  ↑          ↑            ↑
                 やる       やる      人間が判断
```

```bash
git fetch origin develop release-stg
git checkout -B release-stg origin/release-stg
git merge --ff-only develop   # 進められないなら --no-ff
git push origin release-stg
```

**`release-stg` へのマージはテスターへの配布を意味する。** push すると
`flutter analyze` / `flutter test` が走り、通れば App Distribution へ配信されて
テスターに通知が届く。だから `develop` の CI が緑になったことを確認してから流す。
赤いまま流すと配布が失敗し、テスターには何も届かないまま通知だけが濁る。

**`release-prd` へは進めない。** 本番公開は「いつ世に出すか」の判断で、
コードの良し悪しとは別軸。ここだけは人間が決める。

マージしたら **Notion の要件を `検証済み` に更新する。** CI で緑を確認できた時点が
「検証済み」の定義。

マージできなかった場合は、何が引っかかったかを PR にコメントして残す。
次のラウンドの自分、あるいは人間が読む。

### 9. 収束を判定する

**3ラウンド回しても指摘が尽きないなら、それは PR の問題ではなく要件か設計の問題。**
直し続けずに止めて、人間へエスカレーションする。

```markdown
## エスカレーション: 3ラウンドで収束しませんでした

### 繰り返し出ている論点
- <何が毎回引っかかるか>

### 考えられる原因
- 受入基準が曖昧 / 設計方針が要件と噛み合っていない / スコープが大きすぎる

### 提案
- <要件の分割・受入基準の明確化・実装方針の変更、など>
```

レビューが無限に回ると、PR が育ち続けて誰にもレビューできなくなる。
止めることも仕事のうち。

## やらないこと

**`release-prd` へマージしない。** 進めてよいのは `release-stg` まで。
本番公開は「いつ世に出すか」の判断で、コードの良し悪しとは別軸。ここは人間が決める。

**CI が緑になる前にマージしない。** 機械が落ちると言っているものを、
読んだ感触で通さない。ここを崩すと自動テストを整備した意味が消える。

**自分の実装を庇わない。** 同じ AI が書いた PR でも、受入基準に照らして足りなければ
「足りない」と書く。ここで甘くすると、このスキルの存在意義が消える。

**無理に指摘を作らない。** 問題が無ければ「指摘なし」で Approve する。
粗探しのための粗探しは PR を無駄に肥らせるだけで、レビューを儀式にする。

**要件を新規作成しない。** レビュー中に「これも要る」と気づいたら PR コメントへ。

## 報告の書き方

定期実行から呼ばれる前提で、結論を先に。

```markdown
## PRレビュー YYYY-MM-DD HH:MM

**結果**: 修正して再提出 / 指摘なしマージ可 / エスカレーション / 対象なし

### 対象PR
- #NN <タイトル>（<URL>）

### やったこと
- （1〜3行）

### 人間の判断が要るもの
- （あれば。無ければ「なし」）
```
