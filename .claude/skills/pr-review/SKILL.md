# PR をレビューして直し、再提出する

## これが何のためにあるか

AIMARU の自律開発は「要件 → 実装 → PR」までを回している。このスキルはその次で、
**出た PR を読んで、直せるものを直して押し戻す**。

ただし前提を正直に置く。**書いたのも直すのも同じ AI なら、独立したレビューにはならない。**
人間のレビューが持っている「この実装が本当に要件を満たしているか、外から疑う」機能は、
自動化では完全には再現できない。だからこのスキルは次の3つで擬似的に独立性を作る。

1. **PR の説明文を信じない。** 何を満たすべきかは Notion の `受入基準` から読み直す。
   実装者の自己申告ではなく、契約に照らす
2. **直すのは客観的な欠陥だけ。** 設計判断や要件解釈が絡むものは直さず、PR に
   コメントして人間へ投げる
3. **マージしない。** ここだけは人間に残す。自動で書いて自動で通すと、誰の目にも
   触れない変更が本番へ流れる

## 着手する前のゲート

**対象が無ければ何もせずに終わる。** レビュー待ちが無いのに PR を探し回ると、
関係ない変更に手を出し始める。

1. `develop` を base とする open な PR があるか。無ければ「レビュー対象なし」で終わる
2. その PR に**直近30分以内の push があるか**。あれば他のセッションが作業中の可能性が
   高いので触らない
3. その PR が**すでに3ラウンド以上レビューされているか**。あれば収束していないので、
   直さずに人間へエスカレーションする（後述）

複数ある場合は**古いものから1件だけ**。溜まっている PR を並行して触ると、
どれがどのレビューで直ったのか分からなくなる。

## 手順

### 1. 状況を掴む

```bash
git fetch --all --prune
```

PR の差分、CI の状態、既存のレビューコメントを読む。**過去のレビューで
「直さない」と判断されたものを蒸し返さない**ため、コメント履歴は必ず先に読む。

### 2. CI が赤ければ、まずそれを直す

赤い CI はレビュー以前の問題で、しかも原因が機械的に分かる。ログを読んで直す。

- `flutter analyze` の指摘 → 直す
- テストの失敗 → **なぜ落ちたかを切り分けてから**直す。実装が壊れているのか、
  テストが現実に追いついていないのかで対処が真逆になる
- **意図的に失敗させているテスト**（Notion の `期待結果` に「現状は失敗する見込み」と
  書かれているもの）は仕様。通すために実装を歪めない

### 3. 受入基準と突き合わせる

PR に紐づく要件を Notion で開き、`受入基準` を読む。**PR 本文の主張ではなく、
受入基準を1項目ずつ差分で確認する。**

満たしていない項目があれば、それが最優先の指摘。実装が足りないのか、
そもそも解釈が違うのかを見極める。解釈が違うなら直さずに人間へ投げる。

### 4. コードをレビューする

`/code-review` スキルを使う。このリポジトリ固有の観点は
`.claude/skills/notion-implement/references/codebase-notes.md` にまとまっているので、
先に読む。特に踏みやすいのは次。

- Firestore ルールの制約（`create` 時の `resource` は null、クエリとルールの整合）
- リマインダーの状態管理（`reminded` が予定単位でメンバー単位でない）
- table_calendar のカスタム builder が `CalendarStyle` を無視する
- 日付計算（JS の `Date` が存在しない日を繰り上げる、月境界）

### 5. 直すものと投げるものを分ける

ここが判断の中心。**全部直そうとしない。**

| 直す | 投げる（PR にコメント） |
|---|---|
| バグ、境界値の取りこぼし | 要件の解釈が割れるもの |
| テストの不足（受入基準に対応するもの） | 設計の方向性（別の実装方式の提案） |
| `analyze` の指摘、命名やコメントの明らかなずれ | スコープを広げる変更 |
| 既存の書き方から浮いている箇所 | プロダクト判断（何を作るか） |

投げるときは「なぜ自分で直さなかったか」を必ず書く。判断を人間に渡すなら、
判断に必要な材料も一緒に渡す。

### 6. 再提出する

直したら同じブランチへ push する。PR は自動で更新される。

- **force push しない。** 履歴が消えると、前回のレビューで何が直ったか追えなくなる
- **元の実装者の意図を勝手に変えない。** 直すのは欠陥であって、書き方の好みではない
- スコープを広げない。レビュー中に気づいた別件は PR コメントか `docs/open-issues.md` へ

push したら PR にレビュー結果をコメントする。次のラウンドの自分が読む前提で書く。

```markdown
## レビュー（Nラウンド目）

### 直したもの
- <指摘> → <どう直したか>

### 直さなかったもの
- <指摘> → <なぜ人間の判断が要るか>

### 受入基準の充足
- <各項目> → 満たす / 満たさない（理由）

### テスト
- 実行結果: <通った件数 / 実行できなかったものと理由>
```

### 7. 収束を判定する

**3ラウンド回しても指摘が尽きないなら、それは PR の問題ではなく要件か設計の問題。**
直し続けずに止めて、人間へエスカレーションする。

```markdown
## エスカレーション: 3ラウンドで収束しませんでした

### 繰り返し出ている論点
- <何が毎回引っかかるか>

### 考えられる原因
- 受入基準が曖昧 / 設計方針が要件と噛み合っていない / スコープが大きすぎる

### 提案
- <要件の分割・受入基準の明確化・実装方針の変更、など>
```

レビューが無限に回ると、PR が育ち続けて誰にもレビューできなくなる。
止めることも仕事のうち。

## やらないこと

**マージしない。** これが最後の人間のチェックポイント。自動で書いて自動で直して
自動で通すと、誰の目にも触れない変更が `develop` へ入る。`release-stg` /
`release-prd` へのマージも同様で、テスター配布と本番公開はプロダクトの判断。

**自分の実装を庇わない。** 同じセッションが書いた PR でも、受入基準に照らして
足りなければ「足りない」と書く。ここで甘くすると、このスキルの存在意義が消える。

**指摘ゼロで通さない。** ただし**無理に指摘を作るのも同じくらい悪い**。
本当に問題が無ければ「指摘なし、マージ可」と報告する。粗探しのための粗探しは、
PR を無駄に肥らせるだけ。

**要件を新規作成しない。** レビュー中に「これも要る」と気づいたら PR コメントへ。

## 報告の書き方

定期実行から呼ばれる前提で、結論を先に。

```markdown
## PRレビュー YYYY-MM-DD HH:MM

**結果**: 修正して再提出 / 指摘なしマージ可 / エスカレーション / 対象なし

### 対象PR
- #NN <タイトル>（<URL>）

### やったこと
- （1〜3行）

### 人間の判断が要るもの
- （あれば。無ければ「なし」）
```
