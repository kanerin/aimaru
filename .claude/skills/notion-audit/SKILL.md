# Notion 開発ハブの棚卸し

## これが何のためにあるか

AIMARU は Notion の「AIMARU 開発ハブ」を単一の情報源として、AI エージェントが
自律的に開発を回すことを狙っている。その前提が崩れる一番の原因は、**Notion に
書いてある状態と、リポジトリの実態がずれること**。

ずれた瞬間、後続のエージェントは嘘を読んで判断する。「実装済み」と書かれた機能が
無い、「自動化済み」のテストコードが存在しない、「成功」と書かれたテストが実は
落ちている。こうなるとハブは情報源ではなくノイズ源になり、自律開発そのものが
成り立たなくなる。

このスキルはその腐敗を定期的に取り除くためにある。**直すのは Notion だけ**で、
コードには一切触らない。だから頻繁に、安心して走らせられる。

## 絶対に守ること

この3つは、破ると棚卸しが「勝手な開発」に変質してしまう境界線。

**コードを変更しない。** 乖離を見つけても直すのは Notion の記述であって、実装では
ない。「実装が要件を満たしていない」と分かったら、それは Notion のステータスを
`未着手` や `要改修` に戻して報告する仕事。実装するのは別のスキルの仕事。
テストの実行（読み取り目的）は例外として許される。

**要件を新規作成しない。** 要件を起票してよいのは `market-brief` だけで、
それも市場の変化に紐づく形に限られる。エージェントが要件を起票し始めると、誰も決めていない機能でバックログが
埋まる。機能・テスト観点・テストケースの起票は許される。

**実行していないことを「成功」と書かない。** テストを実行できない環境（Flutter SDK
が無い等）なら、`結果` は `未実行` のままにして、実行できなかった事実を報告に書く。
ここで推測を書くと、後続のエージェントが「テストが守っている」と誤認して壊れた
コードを積む。棚卸しが防ぎたかった事故そのものが起きる。

## 手順

### 1. ハブの所在を確認する

Notion のコネクタが使えるか最初に確かめる。使えないなら**その時点で報告して終わる**。
コードだけ調べても Notion に書けなければ意味がない。

既知の ID は `references/hub-ids.md` にある。ID が変わっている、あるいはページが
見つからない場合は `notion-search` で「AIMARU 開発ハブ」を探し、見つけた ID で
`references/hub-ids.md` を更新してからコミットする。

### 1.5. 自分が見ているリポジトリが最新か確かめる

**この手順を飛ばして事故を起こしたことがある。** 別セッションが Notion とコードを
更新している最中に、古い前提のまま同じ更新を上から適用し、重複行を3件作り、
ページ本文を全置換で消した。

棚卸しは「実態と記録を突き合わせる」作業なので、**手元の実態が古いと、正しい記録を
古い情報で上書きすることになる**。これは棚卸しが防ぎたかった腐敗そのものを、
棚卸し自身が作り出す最悪の形。

```bash
git fetch --all --prune
git branch -r -v --sort=-committerdate | head -10
git log --oneline HEAD..origin/develop
```

- `develop` より先に進んでいるブランチがあれば、**そちらが実質の最新**。基準をそこへ
  合わせてから続ける
- 直近1時間以内のコミットがあれば、他のセッションが動いている可能性が高い。
  **書き込まずに報告して終わる**
- 引き継ぎメモ（`docs/` 配下の作業指示ファイルなど）を渡されている場合、
  **それが既に適用済みでないか必ず確認する**。適用済みのものを再適用すると重複が出る

### 2. コードの実態を集める

Notion を読む前に、まずリポジトリの事実を確定させる。順序が逆だと Notion の記述に
引きずられて「書いてある通りに見える」バイアスがかかる。

```bash
# 実装ファイルの一覧
find lib functions/src -type f \( -name '*.dart' -o -name '*.ts' \) | sort

# テストファイルとテスト名
find test integration_test functions/src -name '*_test.dart' -o -name '*.test.ts' | sort
grep -rnE "^\s*(test|testWidgets|it)\(" test/ integration_test/ functions/src/
```

テストを実際に走らせる。**通ったか落ちたかを自分の目で確認する**のがこのスキルの
価値の中心なので、ここは省略しない。

```bash
cd functions && npm ci && npm test && npm run typecheck
cd .. && flutter test
```

どちらかが環境の都合で実行できない場合（Flutter SDK が無い等）、その事実を控えて
おき、該当するテストケースの `結果` は触らない。

### 3. 突き合わせる

4つの観点で見る。それぞれ「Notion に書いてあること」と「今見た事実」を比べる。

| 見るもの | Notion 側 | 突き合わせる事実 | ずれの直し方 |
|---|---|---|---|
| 機能の実装状況 | 機能一覧の `実装状況` | `実装ファイル` のパスが実在するか、中身がその機能を実際に持っているか | 実体が無ければ `未実装`、あるが要件を満たさないなら `要改修` |
| 実装ファイルのパス | 機能一覧の `実装ファイル` | ファイルが存在するか。リネーム・分割されていないか | 実際のパスに更新。想定パス（未実装）なら「（想定）」と明記されているか確認 |
| テストコードの所在 | テストケースの `テストコード` | そのファイルとテスト名が実在するか | 実在すれば `自動化状態` を `自動化済み`、無ければ `未自動化` に戻す |
| テストの結果 | テストケースの `結果` | 手順2で実行した結果 | 通ったものだけ `成功`、落ちたものは `失敗`、実行できなかったものは触らない |

加えて、リレーションの穴も見る。**どの要件にも紐づかない機能**、**どの機能も検証
していないテスト観点**、**親観点の無いテストケース**は、たいてい誰かが片手落ちで
作った行なので報告に挙げる。勝手に繋ぎ直すのではなく、繋ぐべき相手が明らかなときだけ
繋ぎ、迷ったら報告に留める。

### 4. Notion を直す

見つけたずれを `notion-update-page` で反映する。まとめて直すのではなく、
**1件ずつ、何を根拠に直したかを控えながら**進める。後で報告に書くため。

新しく起票してよいのは次の場合だけ:

- 実装ファイルに機能があるのに、機能一覧に行が無い → 機能を起票
- テストコードに実在するテストがあるのに、テストケースに行が無い → ケースを起票

起票するときは、必ずリレーションを埋める。孤立した行を増やすと次回の棚卸しで
また拾うことになる。

### 5. 報告する

この形式で出す。棚卸しは「何も無かった」も価値のある結果なので、ずれがゼロでも
同じ形式で報告する。

```markdown
## 棚卸し結果（YYYY-MM-DD）

### テストの実行結果
- Cloud Functions: N件中N件通過 / 実行できず（理由）
- Flutter: N件中N件通過 / 実行できず（理由）

### 直したずれ（N件）
| 対象 | 変更前 | 変更後 | 根拠 |
|---|---|---|---|

### 起票した行（N件）
| ID | 名前 | 理由 |
|---|---|---|

### 直していない問題（N件）
判断が要る、あるいはコード修正が必要なため Notion 上は変えなかったもの。
| 内容 | なぜ直さなかったか | 誰の判断が要るか |
|---|---|---|
```

**「直していない問題」の欄を空にしたい誘惑に負けないこと。** ここに挙がるものこそ
人間が知りたい情報で、実装スキルの次の入力にもなる。コードの不具合、要件の判断、
権限が要る作業（GitHub のブランチ保護設定など）はすべてここに入る。

## よくある落とし穴

**「実装ファイルがあるから実装済み」と即断する。** ファイルの存在は実装の証拠に
ならない。機能一覧の `概要` と受入基準を読んで、中身が実際にそれをしているかまで
見る。特に「一部実装」と「実装済み」の境目は、受入基準を満たすかどうかで決まる。

**テストが落ちたのを「テストが古い」と解釈する。** 落ちたテストは、実装が壊れている
証拠かもしれないし、テスト自身が現実に追いついていないのかもしれない。棚卸しの
段階では判断せず、`失敗` と記録して「直していない問題」に挙げる。ここで勝手に
どちらかに決めると、本物のバグを見逃す。

**意図的に失敗するよう書かれたテストを直したくなる。** このリポジトリには「まだ
実装されていない要件を先に固定したテスト」が意図的に置かれていることがある。
テストケースの `期待結果` に「現状は失敗する見込み」と書かれていればそれ。
これは仕様であって不具合ではないので、そのまま残す。

**未実行を成功として埋めてしまう。** 棚卸しの信頼性はここに懸かっている。実行して
いないなら書かない。

**ページ本文を `replace_content` で全置換する。** 他のセッションが書いた記述ごと
消える。本文を直すときは `update_content` で該当箇所だけを差し替える。全置換して
よいのは、現在の本文を読んだうえで「まるごと古い」と確認できたときだけ。

**同じ内容の行を作ってしまう。** 新規起票の前に、必ず `notion-search` で同名・
同趣旨の行が無いか確認する。Notion の MCP には削除ツールが無く、**一度作った重複は
エージェントからは消せない**。人間に手作業を強いることになる。
