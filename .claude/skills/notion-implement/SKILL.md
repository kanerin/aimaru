# 要件1件を PR まで運ぶ

## これが何のためにあるか

AIMARU は Notion の「AIMARU 開発ハブ」を単一の情報源として自律開発を回している。
このスキルはその実行部分で、**要件を1件取って、検証可能な終状態まで運びきる**。

工程を「要件調査」「仕様検討」「設計」「実装」「テスト」と分けてスキルにしない
理由がある。工程ごとに分けると、境界のたびにコンテキストが切れて、前の工程の意図が
Notion に残った文字列からしか伝わらなくなる。1機能あたり5回のコールドスタートが
発生し、そのたびに解釈が劣化する。だから**縦に一本通す**。工程はこのスキルの中の
手順として存在する。

## 着手する前のゲート

**やることが無ければ、何もせずに終わること。** これが一番重要な指示。

「プロダクトを改善して」と起こされたエージェントは、対象が無くても何かを見つけて
しまう。頼まれていないリファクタ、些末なテスト、ドキュメントの書き直し。定期実行と
組み合わさると、これが延々と積まれて誰もレビューできない量の差分になる。

だから最初に確認する。

1. `ステータス` が `未着手` かつ `優先度` が `P0 必須` または `P1 重要` の要件があるか
2. 無ければ → **何も作らず**「着手対象なし」と報告して終わる
3. `P2 あると良い` しか残っていない場合も、勝手に着手せず「P2 のみ残っています。
   進めますか」と確認する

CI が壊れている（`develop` が赤い）場合も着手しない。壊れた土台の上に積んでも、
自分の変更が正しいか判定できない。まず CI を直すことを報告する。

## 1回の実行で1件だけ

複数の要件をまとめて進めたくなるが、やらない。理由は3つ。

- PR が大きくなるとレビューが不可能になり、自律開発の唯一の人間チェックが機能しなくなる
- 1件が失敗したとき、どこまで戻せばいいか分からなくなる
- Notion のステータス更新が中途半端な状態で終わる可能性が上がる

要件が大きすぎて1 PR に収まらないと判断したら、**要件を分割するのではなく**
（要件は人間が決めるもの）、その要件に紐づく機能のうち1つを選んで実装し、
要件のステータスは `実装中` のままにしておく。

## 手順

### 1. 選ぶ

要件を1件選ぶ。指定があればそれ。無ければ `優先度` の高い順、同順なら
`要件ID` の若い順。選んだら**要件ページの本文まで読む**。プロパティだけでは
判断材料が足りないことが多く、本文に実装上の注意や既知の落とし穴が書いてある。

`受入基準` を読む。これが今回の完了条件になる。曖昧で判定できないと感じたら、
勝手に解釈を決めずに人間に確認する。ここを推測で埋めると、出来上がったものが
要件と噛み合わない。

### 2. 展開する

要件に紐づく `関連機能` を確認する。

- 機能が既にある → その `実装ファイル` と `実装状況` を見て、何が足りないかを掴む
- 機能が無い → **機能を起票してから着手する**。何を作るかを言語化せずに書き始めると、
  途中で方針がぶれる

機能を起票するときは `レイヤ` `概要` `実装ファイル`（想定パスでよい）を埋め、
要件へのリレーションを張る。この時点の `実装状況` は `未実装`。

### 3. 設計する

`実装ファイル` に挙がっているコードを実際に読む。既存の書き方・命名・コメントの
密度に合わせるのが前提で、このリポジトリの流儀から浮いた実装は入れない。

このリポジトリで特に踏みやすい設計上の地雷は `references/codebase-notes.md` に
まとめてある。着手前に一度読む。Firestore ルールの制約、table_calendar の癖、
リマインダーの状態管理など、知らないと必ず一度は踏むものが並んでいる。

### 4. テストを先に書く

要件に対応するテスト観点とテストケースを Notion で確認する。無ければ起票する。
**テストケースの `期待結果` を先に確定させてから**コードを書く。

これは形式的な儀式ではない。受入基準を機械判定できる形に落とす作業で、ここが
曖昧なままだと「実装した気になって終わる」。先に落ちるテストを書いておけば、
自分の変更が本当に効いたかを自分で判定できる。

テストを書いたら**実行して、意図通り落ちることを確認する**。落ちないテストは
何も守っていない。

```bash
cd functions && npm test        # Cloud Functions
flutter test                     # Flutter
```

Flutter SDK が無い環境なら、その事実を控えて先に進む。ただし後述の通り、
**実行していないテストを「成功」として Notion に書かない**。

### 5. 実装する

テストが通るまで実装する。要件のスコープを超えて手を広げない。途中で別の不具合に
気づいたら、直したくなっても記録に留めて先に進む。混ぜると PR が読めなくなる。

### 6. 検証する

```bash
flutter analyze && flutter test
cd functions && npm run typecheck && npm test && npm run build
```

**通ったものと通らなかったものを、自分の目で確認する。** 実行できなかったものは
「実行できなかった」として扱い、推測で通ったことにしない。

### 7. Notion を更新する

| 対象 | 更新内容 |
|---|---|
| 要件 | `ステータス` → 受入基準を満たし検証できたなら `実装済み`。一部なら `実装中` |
| 機能 | `実装状況` → `実装済み` / `一部実装`。`実装ファイル` を実際のパスに |
| テストケース | `自動化状態` → `自動化済み`。`テストコード` に実在するパスとテスト名。`結果` は**実行したものだけ** `成功` |

要件を `検証済み` にするのは、CI で緑を確認できたときだけ。ローカルで通っただけでは
`実装済み` に留める。

### 8. PR を出す

**ブランチ運用は次のとおり。エージェントが触ってよいのは左端だけ。**

```
作業ブランチ → develop → release-stg → release-prd
   ↑ ここを作る    ↑ ここへPRを出す   ↑ 人間が判断    ↑ 人間が判断
```

- `develop` から作業ブランチを切り、`develop` へ PR を出す
- **`release-stg` と `release-prd` へは直接触らない。** この2つへのマージは
  テスター配布と本番公開を意味する。誰に何がいつ届くかはプロダクトの判断で、
  実装の一部ではない
- `develop` へ直接 push しない。CI が PR で回ることが人間のレビュー機会になっている

1要件1 PR。本文には次を含める。人間がレビューする唯一の場所なので、Notion を
開かなくても判断できる情報量にする。

```markdown
## 対応した要件
REQ-0XX: <要件名>（<Notion URL>）

## 受入基準と、それをどう満たしたか
- <受入基準の各項目> → <どの実装で満たしたか>

## テスト
- 追加したテスト: <パスとテスト名>
- 実行結果: <通った件数 / 実行できなかったものとその理由>

## スコープ外にしたこと
- <途中で気づいたが直さなかったこと、とその理由>
```

「スコープ外にしたこと」を必ず書く。ここが次の入力になるし、意図的に見送ったのか
見落としたのかを人間が区別できる。

## やらないこと

**要件を新規作成しない。** 要件は市場の読みとプロダクトの賭けを含む判断で、人間が
決める。実装中に「これも要る」と気づいたら、PR 本文の「スコープ外」に書いて
人間の判断を仰ぐ。機能・テスト観点・テストケースの起票は許される。

**意図的に失敗するテストを消さない・書き換えない。** このリポジトリには未実装の
要件を先に固定したテストが置かれている（`期待結果` に「現状は失敗する見込み」と
明記されている）。邪魔に見えても、それは仕様。自分が担当する要件がそれを解決する
なら通す、そうでなければ触らない。

**実行していないテストを「成功」と書かない。** 環境の都合でテストが走らないことは
ある。そのとき `結果` を `未実行` のままにするのは失敗ではなく、正しい振る舞い。
ここで推測を書くと、後続のエージェントが「テストが守っている」と誤認して壊れた
コードを積む。

**PR を勝手にマージしない。** 自律開発における人間のチェックポイントは PR レビュー
だけ。ここを飛ばすと、誰も見ていない変更が本番へ流れる。

## 落とし穴

**受入基準を読まずに要件名だけで実装を始める。** 要件名は短く、必ず解釈の幅がある。
受入基準こそが契約。

**既存のテストが落ちたのを自分のせいでないと決めつける。** 落ちたら、まず自分の
変更が原因か切り分ける。`git stash` して落ちるなら元から壊れていた証拠で、それは
それで報告すべき事実。

**Notion の更新を最後にまとめてやろうとして忘れる。** PR を出した直後に更新する。
ここが抜けると、次回の棚卸しで拾われるまでハブが嘘をつき続ける。
