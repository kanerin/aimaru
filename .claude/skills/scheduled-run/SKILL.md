# 定期実行の入口

## これが何のためにあるか

定期実行は**誰も見ていない状態で始まる**。対話で起動されるときと決定的に違うのは、
間違いに気づいて止めてくれる人がいないこと。だから、作業そのものより先に
「今このリポジトリに手を出してよいか」を確かめる必要がある。

このスキルはその門番。実際の作業は `notion-audit` と `notion-implement` がやる。

## 最初に必ずやる安全確認

順番に確認する。**ひとつでも引っかかったら、作業せずに報告して終わる。**
何もしないで終わることは失敗ではない。壊すよりはるかに良い。

### 1. 他のセッションが作業していないか

これが一番よく踏む穴。過去に実際に起きた事故として、別セッションが Notion と
コードを更新している最中に、古い前提のまま上書きして重複行を作り、ページ本文を
消したことがある。

```bash
git fetch --all --prune
git branch -r -v --sort=-committerdate | head -10
```

見るのは次の2つ。

- **`develop` より先に進んでいるブランチがあるか。** あれば、そのブランチが実質の最新。
  そちらを基準にするか、人間の判断を仰ぐ
- **直近1時間以内のコミットがあるか。** あれば他のセッションが動いている可能性が高い。
  その場合は**作業せずに報告して終わる**。並行して書くと衝突する

未マージのブランチが複数ある場合も、統合は人間の判断が要るので着手しない。

### 2. リポジトリの実態と Notion がずれていないか

ずれたまま実装に入ると、嘘を読んで判断することになる。まず `notion-audit` を回す。
棚卸しはコードに触らないので、この段階では安全。

Notion のコネクタが使えない場合は**そこで終わる**。コードだけ進めても、状態を
記録できなければ次の周回が何も分からなくなる。

### 3. CI が緑か

`develop` が赤い状態で積んでも、自分の変更が正しいか判定できない。赤ければ
「CI が赤いので着手しませんでした」と報告して終わる。CI を直すこと自体は
人間の判断が要ることが多い（設定・シークレット・権限）。

### 4. 着手対象があるか

`notion-implement` のゲートに従う。未着手かつ P0/P1 の要件が無ければ、
**何も作らずに終わる**。

誰も見ていない定期実行で一番危険なのは、やることが無いときに仕事を発明すること。
頼まれていないリファクタや些末なテストが積み上がり、レビュー不能な量になる。

## 1周の流れ

```
git fetch → 並行作業の確認 → notion-audit → CI確認 → 着手対象の確認
                ↓ 引っかかった              ↓ 無い
              報告して終了                報告して終了
                                            ↓ ある
                                      notion-implement を1件
                                            ↓
                                        PR を出す → 報告
```

**1回の起動で実装するのは1件だけ。** PR が大きくなるとレビューが不可能になり、
自律開発で唯一の人間チェックが機能しなくなる。

## 報告の書き方

定期実行の報告は**通知で読まれる**。スクロールせずに状況が分かる密度にする。
結論を先に、詳細は後ろに。

```markdown
## 定期実行 YYYY-MM-DD HH:MM

**結果**: 実装1件 / 棚卸しのみ / 着手なし（理由）

### やったこと
- （1〜3行）

### PR
- <URL>（出した場合）

### 次に効くこと
- （次の周回、あるいは人間がやるべきこと。1〜2件）
```

「着手なし」で終わった周回も、必ず理由を書いて報告する。黙って終わると、
仕組みが動いているのか壊れているのか分からなくなる。

## やらないこと

**PR をマージしない。** 自律開発における人間のチェックポイントは PR レビューだけ。
ここを飛ばすと、誰も見ていない変更が本番へ流れる。

**force push しない。** 並行作業があった場合に、他のセッションの成果を消す。

**要件を新規作成しない。** 要件を起票してよいのは `market-brief` だけで、
それも市場の変化に紐づく形に限られる。気づいたことは報告に書いて判断を仰ぐ。

**判断に迷ったら進めない。** 対話なら聞き返せるが、定期実行では聞けない。
迷った時点で「迷った」と報告して止まるのが正しい。
